How it works

  • Split: the key becomes n shares. Any k of them rebuild it; fewer than k reveal nothing at all.
  • Seal: the key file is deleted. A stolen disk or backup now holds only encrypted device keys.
  • Unseal: after a restart, k people enter their shares. The key lives in memory only.
  • Rotate: if a share leaks, make a brand-new key, re-encrypt every device key with it, and issue new shares. The old shares then open nothing.

Unseal the vault

The vault is sealed, so devices cannot authenticate. Paste enough shares, one per line.

Split the key into shares

Give each share to a different person. Creating new shares does not cancel old ones: they all rebuild the same key. If a share is ever leaked, use Rotate the master key below.

Rotate the master key

Use this if a share may have leaked. A brand-new master key is made, every device key is re-encrypted with it, and new shares are issued. Afterwards the old shares rebuild a key that opens nothing. It is all-or-nothing: if anything goes wrong, nothing is changed.

What rotation does not do: it cannot undo a copy of the database that was already stolen, and it does not change the devices' own keys. If a leak may have reached the database too, also issue new device keys.

Test shares

Check that some shares rebuild this server's key. Try it with enough shares, then with one too few. The key itself is never shown.

Seal the vault

This deletes the key file from the disk. Afterwards the server needs enough shares every time it starts. If you lose too many shares, every device key becomes unrecoverable. That is why sealing asks you to prove you hold enough valid shares first.

Stop using sealed mode

The vault is unsealed and the key is held in memory only. To go back to the normal setup, write the key back to its file. (To lock it again, use "Seal the vault" above. To rotate the key, write it back first.)
